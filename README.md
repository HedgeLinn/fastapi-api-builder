# fastapi-api-builder

**把本地集成的服务封装成 FastAPI 接口**，并顺手产出两样东西：给接口调用方看的 `/docs`，给终端用户用的界面。

- 不绑定任何 AI 工具 —— 流程、手册、模板、脚本都是纯文本 + Python，照着做就能跑
- 不依赖构建工具 —— 界面是单文件 HTML，拷过去就能用
- 不碰业务逻辑 —— 只动签名、模型和展示层

---

## 先认清三个角色

**「用户」这个词在本 skill 里是废弃词**，它同时被用来指下面三个人，是歧义的根源。

| 角色 | 是谁 | 跟 skill 的关系 |
|---|---|---|
| **服务开发人员** | 把本地集成的服务封装成接口的人 | **就是 skill 的使用者** —— 读手册、跑脚本、填 CONF |
| **接口调用方** | 别的系统、别部门的技术同事 | **使用对象**：读 `/docs`、直接调 API |
| **终端用户** | 别部门不写代码的同事 | **使用对象**：用界面 |

```
                     ┌─ skill 本体（playbooks + templates + scripts） → 服务开发人员自己用
服务开发人员 ──跑───┤
                     ├─ 产出 A：接口说明 + /docs 换 Scalar          → 给「接口调用方」看
                     └─ 产出 B：用户界面（工作台 / 向导）            → 给「终端用户」用
```

**手册里说"确认"时，指的是服务开发人员确认** —— 他懂业务，AI 不懂。

## 三步跑起来

> **如果服务本身还不存在**（手上只有一个本地脚本），**先读手册 07「服务骨架」** ——
> 它讲清了服务侧该有哪些文件、以及那 15 个必踩的坑（子进程 `-u`、必须串行、
> 产物怎么界定、重启怎么恢复……）。那部分 skill 不给代码模板，给的是经验。
> 下面三步是"服务已经有了、要补文档和界面"。

### 第一步：把 `/docs` 换掉（10 分钟，收益最大）

```powershell
# ① 把 Scalar 脚本复制过去 —— 模板里已经带好了（3.6MB），不用联网下载
#    templates/docs/static/scalar.js  →  <目标服务目录>/static/scalar.js
#    只有要升级 Scalar 版本时才跑：
#    python scripts/fetch_scalar.py --out <目标服务目录>/static

# ② 复制路由
#    templates/docs/api_docs.py  →  <目标服务目录>/api_docs.py

# ③ 改 main.py 三行
#    from api_docs import make_docs_router
#    app = FastAPI(title="XXX", docs_url="/docs-swagger")   # 原生挪走，腾出 /docs
#    app.include_router(make_docs_router(page_title="XXX · 接口文档"))
```

详见 **手册 01**。这一步只是换皮，**`/docs` 里有没有内容还得看第二步**。

### 第二步：把说明搬进代码

`/docs` 里显示什么，取决于代码里写没写。跑：

```powershell
python scripts/fetch_schema.py --url http://127.0.0.1:80xx
```

它会拉下 `openapi.json` 存成快照，并列出**缺什么**：哪些接口没有 `description`、哪些参数没有说明、哪些响应是空壳。然后按 **手册 01** 的流程补。

### 第三步：做一个界面给终端用户

**① 先选定形态** —— 打开 **手册 02 §一「选型卡」**，两张卡（带线框示意）读完就能定：

| | 卡 A · 向导分步 | 卡 B · 工作台双栏 |
|---|---|---|
| 适合谁 | **就想跑一次**的人（偶尔用） | **要管一批任务**的人（天天用） |
| 第一眼 | 只有一件事要做 | 全局都在眼前 |
| 代价 | 老手嫌慢 | 新手会懵 |

> 拿不准就把这两张卡给**服务开发人员**看，让他选 —— 这是本 README 的"拿不准就问"硬规则。
> **不要**为了让他挑就把两套都生成出来（浪费；手册 02 §一 有说明）。

**② 生成**（把 `<形态>` 换成 `console-wizard` 或 `console-workspace`）：

```powershell
python scripts/build_console.py --template <形态> --draft-conf `
       --from-schema data/openapi.snapshot.json --out conf.draft.js
# 看一遍 draft，按业务改（文案、字段映射 —— 手册 02 §三）
python scripts/build_console.py --template <形态> `
       --config conf.draft.js --out console.html
```

> **两份起点怎么选**：`--draft-conf` 是从 schema 推的**草稿**（省事但 TODO 多）；
> 模板的 `<script>` 顶部已经带了一份**能跑的 CONF**（是一份示例配置）。
> **目标服务跟那份 CONF 完全对不上时**才用 `--draft-conf`；否则直接改模板自带的那份更快
> —— 但记住它那份字段名是**举例**，不是模板要求（手册 02 §三）。

产出的 `console.html` 是单文件，丢进目标服务的静态目录即可。

## 拿不准就问（硬规则）

**这个 skill 是给 AI 跑的，但 AI 不能替服务开发人员做业务判断。**

遇到下面这些，**停下来问，不要猜**：

| 拿不准的 | 为什么不能猜 |
|---|---|
| 接口说明的**业务含义** | AI 看代码只能看出"做了什么"，看不出"为什么做"、边界在哪 |
| **哪个状态算成功** | 实测案例里 `partial_failed` 算成功、`invalid` 不算 —— 纯业务判断 |
| **选哪个界面形态** | 谁用、多久用一次、一次跑几个 —— 只有他知道 |
| **该显示哪些字段** | 决定界面显示什么（`CONF.read.*`），猜错就是界面上少一块 |
| **进度机制** | 后端有哪些能力，schema 里看不出来 |
| **输入方式** | 后端签名支持什么 vs 业务需求要什么 |
| **文案措辞** | "输入根目录"还是"要分析的数据目录" —— 业务术语由他定 |
| **能不能改后端** | 改签名、加路由、重启服务，都是有代价的 |

**问的方式：给选项，别给开放题。**

> 给终端用户看的界面，我按业务留了两个方向：
> **A. 工作台双栏** —— 适合一次管好几个任务的人
> **B. 向导分步** —— 适合偶尔用一次的人
>
> 你那边用的人是哪一类？

**这是本 skill 的用法** —— **每种需求都留几个方案，由服务开发人员按业务挑**。
AI 的职责是把方案做出来、把差别说清楚，不是替他决定。

（同样是"拿不准就问"的反面：**别把选项做成十几个**。四个方向已经是上限，
再多就变成把选择题还给他了。）

## 三条纪律

**① 先看签名，再定方案。** 前端能做什么、界面能放什么控件，**完全由后端签名决定**。需求要的签名里没有 → 改后端 / 换来源 / 明确不做，**绝不做假的按钮**。

**② 好看的皮 ≠ 有内容。** 换渲染器解决不了"说明和参数定义缺失"。实测：换皮前后，`description` 覆盖率仍是 1/10、参数说明仍是 0/12。

**③ 变化要关在 adapter 里。** 服务之间的差异只有三处允许变化，其余保持幂等：
- 接口变了 → 重跑 `fetch_schema.py` + `build_console.py`
- 文案/字段变了 → 改 CONF，重跑
- 进度机制变了 → 换 `templates/adapters/` 里的一个函数，界面不动

## 用一次大概多贵（实测）

| | |
|---|---|
| **建一个完整服务**（从裸脚本起） | **~16.8M token，￥18 量级，159 轮** |
| 输入 : 输出 | **202 : 1**（输入占 99.5%） |
| 只换 `/docs`（补文档 + 换皮） | 明显更少 —— 只读代码、改签名，不跑任务 |

**成本主体是"往上下文里塞了多少东西"，不是写了多少代码。** 每轮都要把上下文重发一遍，
读一个 93KB 的源脚本 + 5 份手册，上下文就一路涨上去了。

**省钱的两条**：

- **活派给子 agent，主对话只保留决策** —— 实测主对话成本是子 agent 的 **3.5 倍**（它背着全部历史）
- 验收阶段再让它读大文件，别在探索阶段反复读

## 边界（别期望错位）

- **不做鉴权**：现在假设服务无鉴权。要加，在模板的 `api()` 一个函数里统一注入 header
- **不做跨域方案**：产出的界面是**服务自己发的**（和 `/api/*` 同源），所以没有跨域问题。前端要独立部署才需要代理——那是另一个场景
- **同步接口用不上界面模板**：两个界面模板都是异步任务模型（提交 → 轮询 → 取结果）。接口若是一次请求一次返回，`/docs` 就够了
