# 手册 07 · 服务骨架

> 把本地脚本封成接口时，**服务侧那几十 KB 该有什么、每个坑在哪**。
> 素材来源：一个**成熟实现**（它把每个坑和原因都记在了自己的项目文档里）。
> 状态：本文是经验的抽象，不是代码模板 —— 代码每次都不一样，**坑每次都一样**。

---

## 一、为什么要有这一节

skill 有**界面模板**、**文档模板**，但**服务侧没有模板**。从零建服务时最容易发生的事是：

**功能都实现了，但坑一个不少地踩一遍** —— 因为那些坑不在代码里，在经验里。

实测对比过：同一个脚本，一个从零建的服务 vs 一个跑了一段时间的成熟实现，
功能表一样，但成熟版在被这些问题反复修过之后才稳下来。这一节就是那批经验。

---

## 二、分层：谁管什么

```
浏览器 ⟷ FastAPI ⟷ DB（任务表 + 产物表）
              └─ TaskManager：队列（串行）
                    └─ runner：起子进程 + 传参
                          └─ 你的脚本（一个字不改）
                                stdout ──► progress：解析 ──► 任务进度
```

| 文件 | 管什么 | 备注 |
|---|---|---|
| `main.py` | 建 app、挂路由、启动时恢复在途任务 | 很薄 |
| `api_routes.py` | 路由 | 说明写在这里 → `/docs` 的内容来源 |
| `models.py` | 请求 / 响应模型 | 响应模型决定 `/docs` 里"返回什么" |
| `task_manager.py` | 队列 + 串行 + 取消 + 重跑 | 最厚的一个 |
| `runner.py` | 起子进程、读输出、取消、清理 | 坑最多 |
| `progress.py` | stdout → 结构化进度 | **做成纯函数**（见坑 14） |
| `artifacts.py` | 界定产物、打包下载 | 见坑 6 |
| `db.py` | 持久化 | |
| `config.py` | 配置 + 路径解析 | 相对**服务目录**解析，整目录可拷到别处跑 |

**别做成一个 20KB 的 `main.py`。** 说明文字多没关系，但队列、子进程、持久化这些逻辑要分开——
它们各有各的坑，混在一起改不动。

## 三、15 条坑

### 1. 子进程必须加 `-u`

**为什么**：子进程 stdout 接管道时，CPython 默认**块缓冲**（8KB）。而这类脚本整轮可能只打 30 行（约 2KB）
—— 不加 `-u`，所有输出会**卡到进程结束才一次性吐出来**，进度条和实时日志全部失效。

**怎么做**：`Popen([python, "-u", script], ...)`。这一条最容易漏，而且**漏了不会报错，只是不实时**。

> **已实测**（子进程每秒打一行、共 4 行，父进程用 `for line in proc.stdout` 逐行计时）：
>
> ```
> 不加 -u ：t=4.05s 一次性收到全部 4 行   ← 首行到达时刻 = 进程结束时刻
> 加  -u ：t=0.04 / 1.04 / 2.04 / 3.05    ← 逐行实时
> ```
>
> 4 行远小于 8KB 块缓冲，就已经这样了。**这类脚本整轮往往也就 30 行左右 —— 不加 `-u`，进度条和实时日志是彻底失效的。**

### 2. 读子进程输出：别在"还要干别的事"的那个线程里阻塞读

**为什么**：`proc.communicate(timeout=0.5)` 放在循环里会**丢掉已经读到的输出**，实时日志失效。

**两种可行解，选一种：**

| 解法 | 怎么做 | 什么时候选 |
|---|---|---|
| **A. 读线程 + 轮询取消** | 独立读线程泵 stdout + 主线程 0.25s 轮询取消标志 + `proc.kill()` | 读循环和"决定要不要取消"在同一层 |
| **B. 阻塞读 + 另一线程 terminate** | worker 线程里 `for line in proc.stdout:` 正常阻塞读；取消走**另一个线程** `proc.terminate()` —— 进程死了管道 EOF，读循环自然结束 | 已经有独立 worker 线程在跑任务（本 skill 推荐的服务骨架就是这样） |

**两种都对。** 共同点只有一句：**`for line in proc.stdout` 不能在"同时还要处理别的事"的那个线程里**。
放在独立 worker 线程里阻塞读是**安全的** —— B 就靠这句成立。

> ⚠️ **本手册早期版本只写了 A，还把 `for line in proc.stdout` 一概说成"取消不了"——那是错的。**
> 实测：一个从零建的服务用了 B（worker 线程阻塞读 + `cancel()` 里 `terminate()`），
> 取消工作正常，且代码比 A 简单。

### 3. 必须串行 —— 而原因往往很具体

**为什么**：脚本写盘常见是「写 `{名}_写入中.xlsx` → 删旧正式名 → 改名」，而**临时文件名只由文件名决定、不含任务标识**。
同一个输出目录并发跑，会互相覆盖、产出损坏文件。

**怎么做**：`worker = 1`。别留"以后调大"的口子。

### 4. `max_workers > 1` 要在启动时直接抛异常

**为什么**：坑 3 的原因写在注释里没用 —— 后来人会"顺手调大试试"。
**启动就拒绝**，比事后查损坏文件便宜得多。

### 5. 结果目录怎么定：先选解法，再谈互斥

| | **解法一：共享输出根 + 业务命名** | **解法二：每任务独占子目录** |
|---|---|---|
| 目录怎么定 | 按业务规则命名（如 `{输入名}_{日期}`），**可能重名** | `{输出根}/{task_id}/`，**永不重名** |
| 需要互斥吗 | **要**（同名并发会互相覆盖）→ 409 | **不要** |
| 需要覆盖提示吗 | **要**（同名目录已有历史结果时警告） | **不要** |
| 代价 | 要处理互斥与提示 | **目录会堆积**：同一输入跑 10 次 = 10 个目录，用户得自己认 |
| 适合 | 结果要按业务名归档、同事按名字找文件 | 结果按批次留档、能接受目录堆积 |

**选了解法一，才需要这些：**

- 提交时若该结果目录**已有非终态任务** → **409**
- 若该结果目录**已有历史结果** → 返回 `overwrite_warning`，前端确认，**但不阻止**
- 判互斥要用"实际结果目录"的**归一化路径**，不是用户填的原始字符串

**为什么解法一必须互斥**：不同输入、不同日期可以排队跑；**只有同名目录才互斥**。

> 解法二**顺手绕掉了整个互斥问题**（顺带也绕掉坑 6 和坑 7 的前提）。
> 代价是用户得自己从一堆时间戳目录里找结果 —— 选之前想清楚这个代价能不能接受。

### 6. 产物界定：**先看产物落在哪**，再决定要不要"界定"

| 产物落在哪 | 怎么界定 | 会不会误纳 |
|---|---|---|
| **每任务独占目录**（`{输出根}/{task_id}/`） | **直接扫描该目录就够** —— 里面只有这次任务的东西 | 不会 |
| **共享目录**（用户会在同一目录手工跑脚本） | **必须下面三条来源**，缺一不可 | 会 —— 所以必须界定 |

**★ 本手册早期版本漏了这个前提**，把"三条来源"写成通用要求 ——
但在独占目录下，"扫全部文件"是安全的，反而更简单。**先判断落在哪，再选做法。**

**共享目录下为什么必须三来源**：产物在**用户指定的输出目录**里，不在服务目录，
"哪些是本次任务的产物"必须界定 —— 而且**用户在同一个目录手工跑脚本是常态**，
"扫全部新文件"会把他的手动产物算进服务任务的下载包。

**怎么做**：

1. **主来源**：进度解析器从 stdout 解析出的文件路径
2. **辅助**：在已识别出的目录子树内，按 `mtime >= 任务开始时间` 补漏
   （覆盖"脚本在写主产物之前崩了，但图已经画出来了"）
3. **绝不使用**："输出根目录下所有新文件" —— **用户在同一个目录手工跑脚本是常态**，
   那会把手动产物算进服务任务的下载包

### 7. `rel_path` 基准要统一

**为什么**：同一批产物会**同名不同层**（区域级和汇总级各有一份同名文件）。
扁平化会**静默丢文件**。

**怎么做**（同样**先看独占目录还是共享目录**）：

- **共享目录**：`rel_path` 统一相对**输出根**（不是相对运行目录），
  这样打包时自带运行目录名，多次运行的两个包不会混淆
- **每任务独占目录**：相对**任务目录**即可 —— 包本来就只有一次运行的东西

两种都行，**关键是全服务统一一个基准**，别一个接口相对这个、另一个相对那个。

### 8. 终局判定要有**明确顺序**

**为什么**：多个终态可能同时成立（比如"退出码非 0"和"没扫到任何数据"），**顺序不同结论不同**。

**怎么做**：定一个优先级顺序并写进注释。典型：

```
取消 → 退出码非 0 → 无效（扫不到可处理单元）→ 统计行计数（成功 0 判失败）→ 没有结束标记判失败
```

**特别提醒**：有的脚本遇到"没数据"会**以退出码 0 正常结束**并只写一份空汇总 ——
**绝不能判成成功**。这类"退出码 0 但没干活"的情况要单独一档。

### 9. 重跑语义：必须如实说

**为什么**：这类脚本通常**没有断点续跑能力**，两种重跑（复用目录 / 另起目录）**都是完整重算**，
区别只在写回哪个目录。**前端文案要是写成"复用会更快"，用户就会以为它很快。**

**怎么做**：界面/文档里明说"重跑 = 从零完整重算，不会更快"。
另外：**所有终态都要能重跑**，包括"已完成" —— "结果不满意 / 源数据更新"正是跑完之后才发现的场景。

### 10. 重启恢复：标中断 + 清孤儿 + 清半成品，但**不自动续跑**

**为什么**：服务重启时进程里还有在途任务。而"续跑"对全量重算的脚本是**假概念**，
叫续跑会让用户以为很快。

**怎么做**：

- 在途任务标 `interrupted`
- 清理孤儿子进程（见坑 11）
- 清理 `*_写入中.*` 这类半成品
- **不自动重跑**，界面只提供「重跑（从零开始）」

> 注意：**中断的任务产物列表为空**（产物登记发生在任务正常结束时）。
> 已经产出的部分文件还在输出目录里，但页面不列、不打包 —— 这个行为要在文档里说清楚。

### 11. Windows 上父进程被杀不会带走子进程

**为什么**：这是平台行为，不是 bug。孤儿子进程会继续跑、继续写盘。

**怎么做**：两处兜底 ——
- 运行控制脚本的 stop/restart 用 `taskkill /F /T` 杀**进程树**
- 服务异常崩溃靠启动时的恢复流程：DB 里存了 `child_pid`，用 `tasklist` **确认是 python 再杀**

> 别默认开 `taskkill`：直接 `proc.kill()` 通常就够，而 `taskkill` 有 **PID 复用窗口**的风险。

### 12. 源脚本副本 + 双哈希自检

**为什么**：被封装的原脚本**不许改**，所以常见做法是复制一份副本、只改传参那几行。
但副本会**漂移**：原脚本更新了、副本没跟着更新。

**怎么做**：记**两个不同的哈希**，别混：

- `source_sha256` = 原脚本基线 → 用来判断"原脚本是否已更新、需要重拷副本"
- `copy_sha256` = 副本自身基线 → 服务启动时自检

不一致时**只告警、不阻止启动**。拿原脚本的哈希去比副本，会永远告警。

### 13. 运行控制脚本

**为什么**：服务要长期跑，`Ctrl+C` 那套不够用（要后台、要看日志、要重启）。

**怎么做**：一个 `run.ps1`（或 .sh），提供 `start | stop | restart | status | logs`，
无参数时进交互菜单。把 PID 和日志落到文件。
**启动解释器别写死 `"python"`** —— F5 能跑不代表后台能起，要解析配置里的解释器路径或 PATH，
找不到就直接报错并提示怎么填。

### 14. 进度解析器做成纯函数 → 可单测

**为什么**：正则解析是最容易悄悄错的一块（流水线上的行、两条轴共用同一个标记…），
而它**不需要服务跑起来就能测**。

**怎么做**：`progress.py` 写成**无 IO、无 DB、无全局状态**的纯模块，
喂养好的文本样本断言结果。真实样本存成夹具。

> 实测教训：某脚本的 `[4/6]`、`[5/6]` 标在**两条不同的轴**上（生成图表是两条路径共用的函数），
> 只能靠 phase 判断归属 —— **否则进度会回跳**。这种问题只有单测能锁住。

### 15. 部署坑（四条，每条都真出过事）

- **共享盘权限跟随"服务所在机器上的服务账户"**。用登录用户启动没问题；
  注册成 Windows 服务跑 SYSTEM 账户会**失去 UNC 访问权**，表现为"输入目录不存在"
- **依赖是两套**：服务进程（fastapi/uvicorn/pydantic）+ 子进程（脚本要的 numpy/pandas/…）。
  分开写在 requirements 里。每次任务起子进程都要重新 import 重库，**约 10 秒固定开销**——
  界面上要主动说明"这段时间没输出是正常的"
- **输入路径里的 `{}` 要直接拒绝**：默认值里常放 `{选填单个城市}` 这类提示占位符，
  使用者不改就提交会撞"目录不存在"。给一句人话提示，别让他自己猜
- **路径解析相对服务目录**，整目录拷到别的机器就能跑

## 四、不在这份手册里的（别抄进 skill）

上面的经验是通用的；**具体服务的这些东西不要照搬**：

- 具体的正则与阶段区间（每个脚本的输出格式都不一样）
- 具体的状态取值（`done` / `partial_failed` / `invalid` …按业务定）
- 具体的数据问题（某些目录缺字段之类，那是数据的事）
- 某个服务"曾经做过后来删掉"的功能（别的服务可能正需要）

## 五、怎么用

1. **建服务之前读一遍**，至少做到"知道有哪些坑"
2. 每条坑的**"为什么"要保留** —— 只记结论，下次还是会踩
3. 有些坑不适用（比如脚本不写盘就没有坑 3/6/7），跳过即可，但**要能说出为什么不适用**
4. **每条经验都带着前提 —— 用之前先确认前提成不成立**

   > 本手册是从**一个具体实现**里抽出来的，抽的时候最容易把前提丢掉。
   > **实测教训**：早期版本把"产物界定三来源"写成通用要求，漏了
   > "只在**共享目录**下才必须"；把 `for line in proc.stdout` 一概说成"取消不了"，
   > 漏了"放在**独立线程**里阻塞读是安全的"；只给了"结果目录互斥"一条路，
   > 漏了"**每任务独占目录**"这个顺手绕掉整个问题的解法。
   >
   > **抽象别人的经验时，别只抄结论 —— 把「在什么前提下成立」一起抄下来。**

5. 真有新坑，**回写到这份手册** —— 这份手册的价值就是"坑只踩一次"
