# 手册 02 · 终端用户面：界面形态

> 给**终端用户**用的界面**保留两种形态**，按业务需求二选一。不要每次从零设计。
> 模板：`templates/console/console-workspace.html`、`templates/console/console-wizard.html`
> 状态：两个模板都已跑通验证（对着完整流程，2026-09-18）。

---

## 一、选型卡（读这张就能定，不用生成实物）

> **★ 不要为了"让他看实物挑"把两套都生成出来** —— 那是浪费：要写两份配置、生成两次、
> 封装者还得逐个点开看。**把下面两张卡给他看，他读完就能选。**

### 卡 A · 向导分步　`console-wizard.html`

```
┌──────────────────────────────────────────┐
│   ① ─── ② ─── ③ ─── ④     ← 步骤条        │
│                                          │
│   ┌──────────────────────────────────┐   │
│   │  开始一次任务                     │   │
│   │  选一个数据目录……                 │   │
│   │                                  │   │
│   │  ┌────────────────────────────┐  │   │
│   │  │ 共享盘上的目录路径          │  │   │
│   │  └────────────────────────────┘  │   │
│   │                                  │   │
│   │  ┌────────────────────────────┐  │   │
│   │  │          下一步             │  │   │
│   │  └────────────────────────────┘  │   │
│   └──────────────────────────────────┘   │
└──────────────────────────────────────────┘
```

- **一眼看到**：一个标题、一个输入框、一个大按钮。**没有第二个焦点**
- **视觉**：居中窄栏（820px）、大字号（17px）、圆角大按钮、留白多、无边框卡片（只有柔和阴影）
- **走完全程**：选数据 → 确认 → 处理中（进度条+日志）→ 取结果，**一次只给一步**
- **代价**：老手会嫌点得多

### 卡 B · 工作台双栏　`console-workspace.html`

```
┌───────────────┬────────────────────────────┐
│ 服务名         │  任务详情                   │
│ [+ 新建任务]   │  ┌──────────────────────┐  │
│               │  │ 数据目录   …          │  │
│ 历史任务       │  │ 结果目录   …          │  │
│  ● 已完成  …   │  ├──────────────────────┤  │
│  ● 处理中  …   │  │ ▓▓▓▓▓▓▓░░░  62%      │  │
│  ● 失败    …   │  │ 已完成 6  跳过 1      │  │
│  ● 已完成  …   │  ├──────────────────────┤  │
│               │  │ 结果文件  [打包下载]   │  │
│               │  └──────────────────────┘  │
└───────────────┴────────────────────────────┘
```

- **一眼看到**：左边一列历史任务常驻，右边是当前任务的全部信息（含进度、计数、结果、日志）
- **视觉**：满屏宽、左栏 308px 固定、紧凑（14px 字号）、边框卡片、企业后台观感
- **走完全程**：页面不跳转，点左栏切换任务；信息一直铺开在那儿
- **代价**：新人第一眼会懵

### 对比

| | 卡 A · 向导 | 卡 B · 工作台 |
|---|---|---|
| 适合谁 | **就想跑一次**的人 | **要管一批任务**的人 |
| 使用频率 | 低（偶尔用） | 高（天天用） |
| 一次跑几个 | 一个 | 多个，要对比、要盯 |
| 熟悉度 | 新手 | 老手 |
| 第一眼 | 只有一件事要做 | 全局都在眼前 |
| 代价 | 老手嫌慢 | 新手会懵 |

### 谁来做这个选择

**是「服务开发人员」选，不是终端用户选。** —— 他懂业务，也了解会用的人。
这正是本 skill 的用法：**每种需求都留几个方案，由服务开发人员按业务挑**（和 Scalar 那次一样）。

### 怎么问（拿不准时把上面两张卡给他看）

> 给终端用户看的界面有两个方向，你那边用的人是哪一类？
> **A. 向导分步** —— 一次只给一步，适合偶尔用一次的人
> **B. 工作台双栏** —— 左边任务历史常驻、右边信息全铺开，适合天天用、一次管好几个的人

这就是"拿不准就问"（README 有硬规则）。**但问的是选哪张卡，不是"要不要我生成两套给你看"。**

**默认建议**：两边都不确定就用**卡 A**。它对"不熟悉的人"更宽容，而界面做复杂了没人会看文档。

**两者都要？** 可以各放一个（不同路径）。但**不要试图做一个"兼顾两者"的界面**——那正是产出"四不像"的原因：对新手太复杂，对老手太啰嗦。

## 二、后端需要提供什么（硬依赖）

| 能力 | 必须？ | 用在哪 |
|---|---|---|
| 提交任务 → 返回任务 id | **必须** | 两个模板都要 |
| 查单个任务（状态 + 进度） | **必须** | 轮询 |
| 任务列表 | **必须** | 工作台左栏 / 向导的「以前的记录」 |
| 日志（纯文本） | 强烈建议 | 出问题时终端用户能自己看，不用来找服务开发人员 |
| 产物清单 + 打包下载 | 强烈建议 | 结果交付 |
| 停止 / 重跑 | 可选 | 没有就删掉那两个按钮 |

### ⚠️ 同步接口的服务用不了这两个模板

两个模板都是**异步任务**模型（提交 → 拿 id → 轮询 → 取结果）。

如果目标服务是"一次请求一次返回"（秒回），**不要硬套**——那种服务 `/docs`（Scalar）就够了，专门做界面反而是浪费。判断方法：看接口是返回结果本身，还是返回一个 `task_id`。

## 三、换服务：只改 CONF

两个模板的 `<script>` 顶部都有一块 **`CONF`**，下面所有代码都从它取值。换服务时**只改这一块**。

> ⚠️ **模板里那份默认 CONF 是一份示例配置**（一个示例分析服务）。
> 里面的 `current_item`、`ok_count`、`output_dir` 那些字段名
> **是它的字段名，不是模板要求的**。它是一份"能跑的举例"——让你打开就能看见效果；
> **照抄前先看你自己的后端返回什么**，别为了迁就模板去改自己的后端。

| 字段 | 改什么 |
|---|---|
| `title` / `tagline` / `lede` | 服务名、一句话说明（**用业务语言，不要用接口语言**）。`title` 同时决定浏览器标签；`build_console.py --title` 会覆盖它 —— **改一处即可，别两边都写**（两边不一致时标签会闪一下） |
| `form.*` | 表单标题、说明、placeholder、**预填函数**、**提交时怎么组装请求体** |
| `api.*` | 各接口的真实路径 |
| `states` | 把后端的状态值映射成 `[人话, 色调]`，色调只认 `run/ok/warn/bad/wait` |
| `terminal` | 哪些状态算"结束了"（用来停止轮询） |
| `read.*` | 从任务对象里取字段的函数 —— **这是最需要按服务改的一块** |
| `pollMs` | 轮询间隔 |
| `text.*`（仅向导） | 各步的标题和说明 |
| `msg.*` | 完成/部分完成的提示语 |

**改完必须检查的六处**（漏一处界面就悄悄空一块）：

1. `read.id` —— 任务唯一标识（历史列表拿它当 key）
2. `read.summary` —— 历史列表 / 左栏显示的那一行
3. `read.progress` —— 进度百分比从哪个字段来
4. `read.now` —— "现在在干什么"那句话从哪来（没有就返回空串，别硬编）
5. `read.counts` —— 计数显示哪几个、叫什么
6. `read.artifacts` —— 产物列表怎么取，`fileUrl` 怎么拼

> **这六处 `build_console.py` 都会查**，缺了在生成时直接拦下并列出缺哪几个。
> 它的必需键清单是**从模板代码里自动抠出来的**，不是手写的 —— 所以不会跟模板漂移。
>
> （实测教训：早期版本用的是手写清单，向导模板漏配 `read.summary` 时
> **生成成功、语法通过、界面却在"以前的记录"那行悄悄空着**。改成自动推导后才挡住。）

## 四、多输入的服务

模板默认只有**一个主输入框**。目标服务有多个参数时：

- 在 `CONF.form` 里加字段，并同步改 `newTask()` / `step1()` 里生成表单的那一小段
- **表单区是集中生成的**（工作台在 `newTask()`，向导在 `step1()`），只改那一处
- 别把它做成"万能表单"——参数一大堆、行为靠开关切换，那本身就是反模式（见《优秀接口原则》第 1 条）

## 五、边界

- **跨域**：这两个页面是**服务自己发**的（放 `templates/` 或静态目录，和 `/api/*` 同源），所以没有跨域问题。前端要独立部署时才需要代理
- **鉴权**：现在假设无鉴权。要加的话，在 `api()` 这一个函数里统一注入 header，页面其余部分不用动
- **不自己存历史**：历史来自后端的任务列表接口。前端不落任何本地存储——换电脑、换浏览器都一样
- **不做"结果预览"**：产物是 xlsx / png 这类文件，页面只给下载；要预览得另做，不属于这一版

---

## 六、定稿后

选中的模板 → **单文件**交给目标服务（放到它的 `templates/` 或静态目录，用一条路由发出去）。
它不依赖任何构建工具、不依赖任何外部资源（字体、CDN 全无），拷过去就能用。
