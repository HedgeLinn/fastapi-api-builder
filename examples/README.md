# examples —— 示例产物

**这些不参与运行**，是给服务开发人员写说明文档 / 介绍材料时参考用的：
界面长什么样、接口说明补全后长什么样。

案例：一个异步任务制的分析服务。

---

## ui/ —— 界面示例

给**终端用户**看的界面，做需求时留了四个方向供挑选。**打开不会连上任何服务**
（页面里的 `/api/*` 按示例服务写死），只看长相和交互流程。

| 文件 | 方向 | 特点 |
|---|---|---|
| `index.html` | 挑版本页 | 四个方向并排对比的呈现方式（本 skill 的推荐做法） |
| `a-focus.html` | 聚焦单栏 | 进来就一件事：填 → 跑 → 取。极简留白、大字号 |
| `b-workspace.html` | 后台双栏 | 左列常驻任务历史，右侧工作区。**已采纳为 `templates/console/console-workspace.html`** |
| `c-portal.html` | 门户宽版 | 传统门户式：引导卡 → 详情 → 历史表 |
| `d-wizard.html` | 向导分步 | 四步走，一次只给一步。**已采纳为 `templates/console/console-wizard.html`** |
| `x-early-prototype.html` | 早期单屏原型 | 已被上面四个取代，保留作设计过程记录 |

**四个方向的设计取舍**见《手册 02》。核心区别不在配色，在**布局范式**：

- A / D 面向"不熟悉的人" —— 一次只给一件事
- B / C 面向"熟悉的人" —— 信息铺开，一眼看到全局

## api-docs-completed.py —— 接口说明示例

给**接口调用方**看的 `/docs`，补全前 vs 补全后的对照。

**它不能运行** —— handler 全部留空。它是《手册 01》第四节的参考物：
补什么、补在哪、补成什么样。

实测差距（同一个服务）：

| | 补全前 | 补全后 |
|---|---|---|
| 有 description 的接口 | 1 / 10 | 9 / 9 |
| 有说明的参数 | 0 / 12 | 12 / 12 |
| 成功响应有结构 | 0 / 10 | 9 / 9 |
| 响应模型 | 3（框架自带） | 12 |

用法：拿它当对照，把项目的 `models.py` 和 `api_routes.py` 按这个形状改。
**handler 一律用你原来的实现，只搬签名和模型。**

## 写介绍文档时可以这么用

- **界面部分**：直接打开 `ui/` 里的页面截图，或引用它们说明"同一份
  `openapi.json`，两种界面形态"
- **接口文档部分**：用 `fetch_schema.py` 对一个服务跑一遍体检，
  把"31 处缺口"这类数字放进文档 —— **数字比形容词有说服力**
- **别把示例页面的代码抄进正式项目** —— 正式的用 `templates/` 里的模板 +
  `build_console.py` 生成
